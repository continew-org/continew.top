# ContiNew 文档写作技能

本技能沉淀 ContiNew 开源社区文档的可执行写作规范，供 AI 智能体撰写、重写或评审各项目仓库 `docs/` 目录文档时遵循。各项目仓库的 AGENTS.md「文档（docs/）」一节引用本文件的精简版，**本文件为事实源全本**。

## 何时使用

- 在某项目仓库（continew-starter / continew-admin / continew-app）的 `docs/` 下新建、重写或评审文档；
- 将旧站（VitePress）文档迁移为 Fumadocs 格式；
- 批量统一文档风格时。

## 一、页面准入（先于一切写作）

新建页面前必须逐条回答，答不出任何一条就放弃新建，把内容并入已有页面：

1. **读者是谁**：第一次跑项目的人、二开者、运维，还是查配置的人？
2. **任务或决定是什么**：他打开这页是要完成一件事还是做一个选择？一句话说清；
3. **为什么已有页面装不下**：是内容确实不同，还是只是目录模板里有个位置？
4. **独有信息是什么**：这页至少要有一条别处没有的判断（机制解释、踩坑、边界、取舍）。只有字段表、接口清单、配置默认值的页面不单独成立；
5. **谁维护**：什么代码变更会触发这页同步？没人答得出的页面不建。

目录结构服务于用户任务，不是每个代码模块、配置类别都必须对应一篇文档。**为导航整齐而创建的内容空泛的 index 正文页，同样过不了准入。**

## 二、文档类型（一页只有一个主类型）

每页开始前先选类型，正文结构跟着类型走，不得混装：

| 类型 | 读者状态 | 正文形态 | 禁止事项 |
|:-----|:---------|:---------|:---------|
| Tutorial（教程） | 第一次上手 | 一条可完整跑通的任务主线：按步骤做完得到可验证结果 | 不塞全部配置解释、不横向铺所有选项 |
| How-to（操作） | 有基础，要办一件具体事 | 问题 → 步骤 → 验收点 | 不讲机制原理，链接 Explanation |
| Explanation（解释） | 想懂机制与取舍 | 机制、边界、为什么这样设计 | 不放操作步骤清单 |
| Reference（参考） | 查值 | 键、类型、默认值、适用版本，允许完整 | 不占主学习路径，优先生成 |

Admin 的主体是 Tutorial + How-to（启动、开发第一个功能、部署、使用某功能）；Starter 的主体是模块 Explanation + Reference。功能手册（manual/）描述页面操作后果时是 How-to；接口、表、权限码等实现细节放页尾「实现索引」小节，不作为正文骨架。

## 三、迁移保全（改写旧文档前必须执行）

旧站由维护者长期人工写作，是**编辑资产**而不是待清洗素材。迁移或重写任何旧页前，先逐段标记「保留 / 更新 / 合并 / 淘汰」并写明理由，且必须单独提取以下内容，缺一不可：

1. **任务顺序**：旧文的步骤为什么是这个先后；
2. **维护者判断**：「必须空库」「先跑通再定制」「别启动错类」这类强断言；
3. **踩坑与报错特征**：真实故障的样子、排查顺序、最常见的错误原因；
4. **验收点**：做到什么现象才算成功（如「登录页出现图形验证码」才证明前后端联通）；
5. **项目声音**：作者口吻的动机与立场叙述（可移至官网 About，但不得静默丢弃）。

源码负责校验事实，旧人工文档负责提供意图、顺序与经验。**禁止拿着新目录模板直接重写旧内容。** 同时明确淘汰项：重复的祝贺与求 star 段落、IDE 截图堆砌（保留可复制命令）、混入正文的 FAQ、过时或不安全的操作（如 `chmod -R 777`）。

## 四、目录组织

按「叙事式学习路径」组织，而非按代码模块平铺：

```
docs/
├── index.mdx              # 分区入口（着陆页）：是什么一句话 + 导航卡片，不复述正文
├── meta.json              # 分区标题、图标、页面顺序；root 分区标 root: true
├── guide/                 # 指南：introduction → quick-start → 第一个业务功能（Admin）或 configuration（Starter）
├── modules/               # 功能模块（Starter）：单实现一版 .mdx；多实现为目录（index 入口 + 子实现各一篇）
└── reference/             # 参考：properties / dependencies / environment / faq / changelog / security
```

原则：

- 用户的阅读路径是「跑起来 → 开发第一个功能 → 查某功能完整用法 / 查配置」，组织方式要服务于这条路径；
- **多实现模块拆分**：含多个子实现的模块（如 cache、auth、extension），按「目录 + 子实现各一篇 + 模块 index 入口」组织，让侧边栏可直达具体组件；单实现模块保持单篇；
- **Root Folder**：每个项目分区在 meta.json 标 `root: true`，构成官网侧边栏顶部的项目切换器；
- **模块 README 做导航卡片**：多模块项目的代码模块内保留简版 `README.md`，只放「是什么 + 坐标 + 一句话用法 + 完整文档链接」；
- 用户功能手册按用户主题合并（账号与组织、权限、文件与存储、通知与消息等 10~12 个主题），不按 Controller/表一一建页。

## 五、frontmatter（必填）

```mdx
---
title: 页面标题
description: 一句话描述本页解决什么问题（用于 SEO、搜索摘要、OG 图片、llms.txt）
---
```

- `title` 用**中文为主**；技术专名与协议名（Sa-Token、MyBatis Plus、WebSocket、MQTT、Excel、POI、CRUD）可保留英文原文，不做机械翻译；
- `description` 一句话说明价值，不空、不复述标题。

## 六、链接策略（按运行时语义写）

- **跨模块/跨分区引用**：用绝对发布路由 `/docs/<project>/...`（如 `/docs/starter/modules/cache`），不带 `.mdx` / `.md` 扩展名；
- **MDX 组件属性（`<Card href>` 等）**：一律用**绝对发布路由**。页面 URL 无尾斜杠，`./child` 会按浏览器规则解析到父目录的同名页，禁止在组件属性中使用相对路径；
- **同目录内普通 Markdown 链接**：可用相对链接（如 `./crud`），但构建后必须通过产物级链接检查；
- 外部链接给完整 URL。

**验收标准是产物不是源文件**：构建后解析 `out/**/*.html` 的内部 `<a href>` 做存在性检查，普通 Markdown 相对链接会被编译器改写，组件属性不会。任何一处 404 都视为未完成。

## 七、写作风格规范（活人感写作 · 技术文档版）

技术文档同样是人在说话：这个人知道实现细节，也知道哪里会踩坑，愿意把来龙去脉讲清楚。不喊口号、不替读者感动、不把常识包装成洞察。判断可以直接下，但依据要放在附近。

### 硬禁令

| 禁令 | 说明 |
|:-----|:-----|
| 不用破折号 `——` | 改成分句、括号或另起一句 |
| 不写翻案腔 | 「不是 A，而是 B」「值得注意的是」「需要注意的是」「说白了」「先说结论」全部禁用 |
| 不写商业与模型黑话 | 赋能、一站式、无缝、极致、助力、打造、综上所述 |
| 不把动词名词化 | 「完成了对配置的加载」改「加载配置」；「实现了效率的提升」改「快了多少」 |
| 不在末段摘要全文 | 讲完就停，不强装升华 |
| 不开篇复述标题 | 第一句直接进入读者何时需要本页，删掉标题已能表达的句子 |

### 模板腔自查（比禁词更重要）

以下高频词超过正常密度即判为模板化写作，必须重写具体内容：

- 「开箱即用」「基于」「提供」「完整」「统一」「自动」「无需」连续铺陈；
- 页面统一按「功能入口 → Controller → 接口前缀 → 数据表 → 字段清单 → 接口权限码 → 相关源码」展开（这是代码索引，不是用户文档）；
- 每段都以「`xxx` 是……」开头。

有效的写法：第一段说清读者何时需要这页、读完能做成什么；正文按用户要做的事组织；每个配置表至少跟一句「什么时候要改它」。

### 段落推进

- 一段只做一件事：讲动作、补背景、解释原因、承认疑点、给判断，选一个；
- 新段落必须带来一样新东西：新的事实、例子、区别、后果都算，同一观点换说法不算；
- 先让主语和动作出现，再接时间、原因、条件。

### 材料要求（事实源优先级）

每条结论必须能指到一样看得见的东西：**starter 源码（类名 / 默认值 / 异常）> continew-admin 实际用法（示例 / 组合 / 最佳实践）> 上游官方文档**。

- admin 排第二而不是第一：它是消费方，可能用自己的扩展点覆盖默认行为，API 签名必须以 starter 源码为准；
- **示例分层**：API 与配置示例用通用场景（`Goods`、`MyService`）；**Tutorial 必须用一个真实、可完整跑通的业务案例**（如岗位管理），禁止把教程示例抽象成占位符；
- **配置项归 starter，配置值归 admin**：框架级配置项的定义写 starter 文档；admin 给这些键填的具体值写 admin 文档；
- 每个模块文档末尾加「相关源码」或「完整参考实现」链接，指向具体仓库文件（Admin 与 Starter 都要，指向 `dev` 分支真实路径）。

## 八、组件用法

代码块标注语言（```xml、```yaml、```java、```bash），命令给可直接复制执行的完整形式；配置项/类名/注解/坐标用行内代码（`）包裹。

需要处使用 Fumadocs 组件：

```mdx
<Cards>
  <Card title="标题" description="一句话" href="/docs/starter/reference/properties" />
</Cards>

<Callout type="info|warn|error">提示内容</Callout>

<Tabs items={['实现A', '实现B']}>
  <Tab value="实现A">...</Tab>
  <Tab value="实现B">...</Tab>
</Tabs>

<Steps>
  <Step>第一步</Step>
  <Step>第二步</Step>
</Steps>
```

注意：`<Card>` 的 `href` 必须是存在的无扩展名发布路由（见第六节）；依赖坐标给 Maven `<dependency>` 形式，`groupId` 为 `top.continew.starter`，不写 `<version>`（由 BOM 统一供给）。

## 九、单一事实源与重复门禁

- **一个事实只能有一个详细事实源**：完整配置表、依赖版本表、环境变量清单只在一处维护（Reference），其他页面只列本任务所需子集并链接过去；
- 配置项、默认值、依赖版本**优先自动生成或自动校验**（来源：`spring-configuration-metadata.json`、POM、lockfile、OpenAPI），人工只解释选择、限制与后果；
- 新页面与现有页面行内事实重合度超过约三分之一时，必须合并而不是并存；
- 代码块示例标注可运行前提（依赖、Bean、上下文），关键示例应能编译。

## 十、版本标注

- 示例的版本号给**具体值**（如 `2.17.0`），并附 Maven Central 查询链接；
- 不写「当前版本 x.x.x」这类易过时表述；版本相关内容标注适用范围（如「2.x 基于 Spring Boot 3.x」）；
- 官网汇聚的是 `dev` 分支文档，涉及 dev-only 能力时在正文显式说明「自 x.x.x 起 / 尚未随正式版发布」，避免与最新 release 混淆。

## 自检清单（写完逐条过）

**准入与类型**
- [ ] 能答出读者、任务、独有信息三问
- [ ] 全文只有一个主文档类型

**事实**
- [ ] 配置项、类名、默认值、路径、版本与源码一致
- [ ] 每个判断后面跟了依据（类名/配置键/默认值/报错串/真实用法）
- [ ] 代码示例标注了依赖与前提，关键示例能编译

**结构**
- [ ] 第一段直接说明读者何时需要本页
- [ ] 正文按用户任务组织，接口/表/权限码只在页尾实现索引
- [ ] 完整表格没有在第二处手工重复

**风格**
- [ ] 无 `——`、翻案句式、商业黑话、末段升华
- [ ] 没有用「基于/提供/开箱即用」铺满段落的模板腔
- [ ] 每段都推进了新信息

**链接与迁移**
- [ ] 组件 href 全部为绝对发布路由；站内链接无 `.mdx` 后缀
- [ ] 改写旧文档时提取了任务顺序、判断、踩坑、验收点四项
- [ ] frontmatter 含中文 title 与一句话 description
